# Frontend / Backend Contract

The wire contract is defined in code, not duplicated in this document.

- Backend routes: `api/routers/`
- Backend request/response models: `api/models/`
- Frontend runtime schemas: `frontend/src/lib/schemas.ts`
- Frontend HTTP client: `frontend/src/lib/api.ts`
- Application routes: `frontend/src/App.tsx`
- Live endpoint schema: FastAPI OpenAPI generated by the running backend

This file records only the invariants that must remain stable across changes.

## Boundaries

The backend exposes five route families: upload, health, search, policy, and remediation. Routers are thin HTTP adapters; domain behavior belongs in `codegraph/`.

The frontend has four user routes: `/`, `/upload`, `/policy`, and `/settings`. Server state uses TanStack Query. Successful API payloads are validated at the browser boundary with Zod before entering UI state.

## Schema Alignment

A backend payload change is incomplete until the matching frontend schema and affected client/tests are updated in the same change. Do not maintain parallel handwritten TypeScript interfaces for wire payloads when a Zod schema already owns the shape.

Required properties must not become optional in the frontend merely to mask backend drift. If compatibility is intentional, encode it explicitly in both boundary models and test the transition.

## Identity and Provenance

Workspace, revision, finding, method, source-range, and candidate identities are not presentation details. The client must preserve identifiers returned by the backend rather than reconstructing them from labels or source text.

Source locations, hashes, and verification evidence must be displayed from backend data. The frontend must not infer that a remediation succeeded from UI state, a generated diff, or model confidence.

## Errors and Requests

The backend stamps responses with `X-Request-Id`. Unhandled server errors return a generic `{"error": "internal", "request_id": ...}` envelope while the traceback remains server-side.

Expected 4xx responses may use structured error envelopes defined by the route contract. The frontend should surface actionable messages without depending on private traceback text or undocumented exception strings.

Long-running requests must remain cancellable where the client exposes cancellation. Streaming upload/progress behavior must preserve the server-defined event shape rather than synthesizing completion locally.

## Remediation UI

The UI may preview a candidate before application, but it must preserve the distinction between proposal, verification, and apply. A candidate is acceptable only when the backend reports the required deterministic gates as successful. Refusal and unavailable verification are first-class outcomes, not generic failures to hide.

## Change Checklist

When the API contract changes:

1. update the backend model and route;
2. update `frontend/src/lib/schemas.ts` and the API client if needed;
3. update backend and frontend contract tests;
4. verify request IDs, error envelopes, identifiers, and nullability remain intentional;
5. run the relevant backend tests plus `cd frontend && yarn lint && yarn test && yarn build`.

Do not add endpoint inventories or example payload copies here unless they express a stable invariant. Use the running OpenAPI document and source models for exact current fields.
